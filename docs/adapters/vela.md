# Vela adapter design

**Status:** Designed; not implemented.
**Scope:** Boundary checks around Vela local-development flows, not TEE assurance.

## Why an adapter is needed

Vela is a TEE-based confidential execution solution. Its documentation describes application logic running inside a TEE, data encrypted in memory, and cryptographic attestation of computation. [Vela introduction](https://docs.horizen.io/vela/introduction/)

Those properties do not remove all public application surfaces. The documented local sample includes:

- WASM artifact upload and an onchain deploy request;
- an application identifier;
- a registered user P-521 public key;
- deposit and withdrawal-related transactions;
- an onchain descriptor/WASM fingerprint check;
- encrypted events returned to the registered user; and
- a `deanonymize` operation for authorized auditors.

See [Vela's private-app walkthrough](https://docs.horizen.io/vela/getting-started/hello-world/). EVM Privacy CI must make those surfaces explicit in policy rather than implying that every part of an app is private.

## Adapter objectives

1. Exercise the documented local development environment using **test-only** data.
2. Inspect public EVM transactions, receipt logs, emitted topics/data, selected storage, and artifact metadata.
3. Verify that a policy-classified test sentinel does not appear in a forbidden public surface.
4. Require an explicit disclosure rationale for public application IDs, state roots, P-521 public keys, deposits/withdrawals, and deanonymization controls.
5. Detect drift between an approved WASM artifact hash and the artifact supplied to a test deployment.

## Non-objectives

The adapter does not:

- read enclave memory;
- evaluate real hardware attestation;
- verify remote-attestation chains;
- establish ciphertext security;
- recover encrypted Vela events;
- declare deposits or withdrawals unobservable;
- validate Vela production readiness.

Vela’s current documentation says the environment is active development, Docker-local, and uses an emulated TEE. There is no production testnet or mainnet deployment at present. [Vela limitations](https://docs.horizen.io/vela/limitations/)

## Inputs

```yaml
vela:
  applications:
    - id: private-payroll
      environment: local-docker
      wasm_artifact: artifacts/payment_app.wasm
      approved_sha256: "<release artifact SHA-256>"
      commands:
        setup: ./scripts/start-vela-test.sh
        test: ./scripts/run-private-payroll-test.sh
      protected_test_sentinels:
        - asset: payroll.amount
          fixture: test-only-payroll-amount
        - asset: payroll.employee_id
          fixture: test-only-employee-id
      permitted_public_surfaces:
        - application_id
        - state_root
        - user_p521_public_key
      authorized_disclosures:
        - operation: deanonymize
          role: AUDITOR_ROLE
          purpose: Authorized lawful/audit disclosure.
```

Values marked as sentinels are logical fixture names, not raw values stored in the policy file. The test harness obtains the literal from its local test fixture or generates a high-entropy per-run value. The policy must never hold a secret or production personal data.

## Probe flow

```text
policy + fixture values
        |
        v
start documented Vela Docker local environment
        |
        v
deploy approved WASM -> compare local SHA-256 to policy
        |
        v
execute test-only register / deposit / transfer / withdrawal flows
        |
        +--> capture RPC request input, transaction, receipt, log, storage snapshot
        |
        +--> apply sentinel and transform checks
        |
        v
report policy violations and coverage gaps
```

## Checks

### VC-VELA-001 — Artifact identity drift

Report an error when the WASM SHA-256 presented to the local deployment flow differs from the approved policy hash. This does not prove the WASM behavior is safe; it preserves the reviewed-artifact boundary.

### VC-VELA-002 — Public-envelope sentinel disclosure

Report an error when a raw protected test sentinel is found in:

- top-level transaction input;
- decoded method arguments;
- receipt log topics/data;
- configured public storage slots;
- public getter result;
- unencrypted test report generated by the adapter.

The test must use values that are unique and non-production. Low-entropy sentinels such as `100` cannot distinguish a direct disclosure from unrelated test data.

### VC-VELA-003 — Undeclared disclosure path

Report a warning/error when the test trace contains a configured Vela public surface that is not listed in `permitted_public_surfaces` or `authorized_disclosures`.

### VC-VELA-004 — Deanonymization control review

Report a review finding when a policy declares `deanonymize` without a specific role, purpose, and owner. This is not a proof that the role check works; it creates an explicit audit checklist item.

## Reporting examples

```text
ERROR VC-VELA-002
Asset: payroll.amount (confidential)
Surface: transaction_calldata
Operation: deposit
Evidence: test sentinel appeared as decoded argument `amount`
Fix: Use an approved private request representation or revise the policy to
document why this amount is necessarily public.
```

```text
REVIEW VC-VELA-004
Operation: deanonymize
Issue: Policy declares authorized disclosure but omits a named role.
Required: role, purpose, policy owner, and linked manual-review evidence.
```

## Test requirements

- The Vela runner uses a disposable Docker volume and local test chain.
- A test runner must not load repository `.env`, wallet configuration, or production credentials.
- A local RPC capture is sanitized before it becomes a report artifact.
- Tests pin Vela release/compose versions and record those versions in output.
- Vela adapter integration tests are optional/marked until Vela provides a stable test environment; normal policy validation must remain runnable without Vela.

## Open decisions

1. How to collect local storage safely without relying on a fragile fixed layout.
2. Whether encrypted-event ciphertext length and timing should be emitted as informational metadata in a later version.
3. How to validate an authorized disclosure policy against Vela’s future granular deanonymization controls.
4. Which command interface becomes stable enough for a release-quality adapter.
